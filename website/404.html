The problem

Autonomous agents need more than instructions.

Long-running AI agents can be manipulated by prompt injection, hostile tool output, untrusted files, compromised integrations or gradual task drift. Once an agent is influenced, normal permissions may be used in abnormal ways.

01

Prompt injection

External content can redirect an agent toward actions outside the original task.

02

Tool misuse

Legitimate tools can become the path for unauthorized filesystem, network or process effects.

03

Long-running drift

Risk can emerge from sequences of individually plausible actions over time.

04

Weak evidence

Logs that depend on the agent are not enough when the agent itself may be compromised.

The KECHAA approach

An independent authorization layer between agents and effects.

KECHAA separates an agent's reasoning from the authority to execute. Actions are evaluated against task contracts, policy, session identity and trusted execution history before a signed grant is issued. The Linux execution architecture is designed to connect those decisions to operating-system containment boundaries.

Authorize explicitlySingle-use grants bind exact context and effect envelopes.
Remember historyPrevious denials and tool events can influence later decisions.
Fail closedUnsupported effects are denied instead of silently allowed.
Product capabilities

Six building blocks for safer agent execution.

KECHAA's product model is intentionally focused: govern what agents can execute, retain trusted state, and make suspicious sequences actionable.

✦

Trusted Authorization

Problem: broad permissions are hard to revoke once an agent is running.

KECHAA: signed, single-use grants bind execution to the reviewed action, policy version, session and effect envelope.

Benefit: developers can approve bounded operations without handing over open-ended authority.

▣

Task-Bound Execution

Problem: agents often operate beyond the task they were originally given.

KECHAA: task contracts define permitted roots, executables, write scope and session lifetime.

Benefit: agent work is framed by a durable security contract instead of a prompt alone.

⟲

History-Aware Authorization

Problem: dangerous behavior may appear as a sequence of small, plausible actions.

KECHAA: later decisions can consider trusted execution history, previous denials, posture and session state.

Benefit: policy can respond to patterns, not just isolated requests.

⬡

Agent Containment

Problem: a compromised agent should not be able to opt out of security boundaries.

KECHAA: supervised launch and Linux containment design connect authorization to OS-level restrictions for supported offline paths.

Benefit: enforcement is designed to live outside the agent's reasoning loop. Linux certification is still pending.

!

Quarantine and Recovery

Problem: suspicious activity needs a response workflow, not just an alert.

KECHAA: posture changes, quarantine and recovery paths help operators stop, review and re-authorize sessions.

Benefit: response becomes part of the execution lifecycle.

⌁

Agent Ecosystem Security

Problem: tool and MCP ecosystems can create external effects outside a shell command.

KECHAA: MCP-style tool requests require explicit offline effect contracts; unsupported external effects fail closed.

Benefit: integrations can declare effects instead of bypassing authorization.

How it works

From task definition to containment response.

  1. 1

    Define the task

    An operator confirms the run contract: roots, executables, write permission and lifetime.

  2. 2

    Request authorization

    The agent or adapter submits an action or declared tool effect.

  3. 3

    Evaluate policy and history

    KECHAA checks the current action, session, task authorization and trusted execution history.

  4. 4

    Issue or deny a grant

    Allowed work receives a signed single-use grant; suspicious work can require approval or be denied.

  5. 5

    Govern execution

    The Linux architecture is designed to launch supported work through a supervised containment boundary.

  6. 6

    Record and respond

    History and audit records support posture changes, quarantine and recovery.

FAQ

Clear answers for evaluators.

Is KECHAA production-ready?

No. KECHAA is an experimental alpha and should be treated as a security prototype until Linux certification and broader reliability work are complete.

Does KECHAA prevent prompt injection?

No product can guarantee that an agent will not be influenced by malicious content. KECHAA focuses on constraining what the agent can execute when its reasoning is no longer trustworthy.

Is Linux containment certified?

Not yet. LC-001 through LC-013 are prepared but still require execution in a disposable Linux VM.

Does KECHAA fully mediate MCP?

No. KECHAA currently supports effect-contract authorization for MCP-style tool requests. Full MCP protocol proxying is not implemented.
